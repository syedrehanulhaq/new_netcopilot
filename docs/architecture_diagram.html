What is the Agentic AI Loop?

The AI keeps looping until it has enough data to answer
💬
1 · You send a message
"Is BGP to pe2 healthy?"

FastAPI forwards it to the LLM together with:
• full conversation history
• list of available tools
• device inventory
🧠
2 · AI decides what to check
LLM returns a tool call instead of plain text:

junos_get_bgp_summary
{"device": "pe1"}

It picked the right tool from the list — it was not told to use it.
🔁
3 · Result goes back → loop
Dispatcher runs the tool on the real device.
The output is appended to the conversation.
LLM is called again.

→ If it needs more data, it calls another tool.
→ If it has enough, it writes the final answer.
↑ Tool result goes back to the LLM as a message  ·  loop repeats until LLM returns plain text with no tool calls  ·  typically 1–4 iterations per question ↑

What does the Tool Dispatcher do?

Routes every tool call name to the right Python code
LLM tool call arrives →

prometheus_* e.g. prometheus_query

Full example — "Is BGP down on pe1?"

Watch the agentic loop + dispatcher in action. The LLM makes two tool calls before answering.

👤 Engineer
(Slack)
message "BGP to pe2 is down, what's going on?"
POST /slack/command → FastAPI → JWT verified, role = noc-ticket
🧠 LLM
(Iteration 1)
tool call junos_get_bgp_neighbor_status → {"device":"pe1","neighbor":"10.0.0.2"}
LLM chose this from the tool list — it was not scripted
🚦 Dispatcher
route prefix = junos → junos.py → PyEZ NETCONF → pe1
Returns: {"state":"Active","last_reset":"00:03:12","reset_reason":"Notification: hold time expired"}
🧠 LLM
(Iteration 2)
tool call run_playbook → {"intent":"bgp_down","device":"pe1","neighbor":"10.0.0.2"}
LLM decides to run the full BGP diagnostic playbook for more evidence
📋 Playbook
Runner
playbook bgp_down: check neighbor → check route table → check interface MTU → check syslog
Each step calls call_tool_unprefixed() which auto-adds "junos_" prefix → real device calls
Returns: {"severity":"Critical","evidence":{"hold_time_expired":true,"mtu_mismatch":true}}
🧠 LLM
(Final)
answer No more tool calls — writes plain text response
"BGP to pe2 is Critical. Hold timer expired 3 min ago due to MTU mismatch (pe1=1500, pe2=9000). Recommend fixing MTU on ge-0/0/1."
👤 Engineer
(Slack)
response Answer posted back to Slack channel
FastAPI streams response → Slack API → engineer sees full diagnosis in channel

Jira — two paths, one system

Path A — LLM asks Jira (48 tools via mcp-atlassian)

→
Engineer: "Create a P2 Jira ticket for the BGP issue on pe1"
→
LLM calls mcp-atlassian tool (e.g. jira_create_issue)
→
Dispatcher → MCPClient → SSE → mcp-atlassian sidecar on :8104
→
mcp-atlassian → Jira REST API → ticket created
✓ 48 tools: search, create, update, transition, sprints, comments…
✓ Atlassian-maintained — zero maintenance for us

Path B — Slack command (4 tools via jira.py)

→
Engineer types /noc ticket BGP down on pe1 in Slack
→
Slack slash-command handler in FastAPI parses intent
→
Calls jira.py directly — no LLM involved, no MCP overhead
→
jira.py → httpx → Jira REST API → ticket created instantly
✓ Instant: no LLM round-trip
✓ 4 tools: create · close · comment · update fields
