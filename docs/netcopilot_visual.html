🚀 Startup sequence
5 things happen in order before the first request is served
💾
1 — Init memory.db
Creates the SQLite conversation history database. Stores the last 12 exchanges per user so the LLM remembers context across messages. The LLM does not have built-in memory — this file is its memory.
🔔
2 — Init alerts.db
Creates the alerts database. When Prometheus/PagerDuty fires an alert via /alerts/ingest, it is stored here keyed by Slack channel ID. The Slack handler reads it when /noc investigate is called.
📋
3 — Load device registry
Reads devices.yaml into memory. Every subsequent get_vendor("pe1") call returns instantly from this cache. The LLM system prompt is also populated with this inventory so the AI knows which vendor to use for each device.
🔌
4 — Connect MCP client
Opens a persistent SSE connection to mcp-atlassian (port 8104). Sends an initialize handshake, then calls list_tools() to discover all 48 Jira tools dynamically. These are stored in memory prefixed as jira_create_issue, jira_search_issues, etc.
⚡
5 — Create Tool Dispatcher
Instantiates ToolDispatcher(mcp_client=...) as a singleton. This is the routing brain for all subsequent tool calls. Server is now ready to accept requests.
⚙️ How settings and credentials work
Every get_setting("KEY") call checks three places in order. No restart needed to change values.
PRIORITY 1 — HIGHEST
🗄️
settings.db (SQLite)
Admin edits a value in the web UI at /admin/settings. Stored in SQLite. Takes effect on the next request — no restart. This is the intended way to manage production secrets.
PRIORITY 2
🌍
Environment variable
Set in .env file (dev) or Docker env vars (production). Used when no SQLite value exists. Good for initial setup and container deployments.
PRIORITY 3 — LOWEST
📄
Default value
Hardcoded fallback in the source code. E.g. model defaults to gpt-4.1-mini, port defaults to 830. Only used if neither DB nor env var is set.
Why this matters: Device credentials (JUNIPER_PASS, etc.) are fetched by credentials.get_secret() inside each tool call, not at startup. Rotating a password in the UI takes effect immediately on the next SSH connection — no restart, no dropped sessions.

Three vendors, three adapters, same pattern. All run in a thread so they don't freeze the web server.

Why NETCONF?
Versioned schema, no text parsing, most reliable
Credentials

🔴 Nokia SR OS
18 tools · nokia_*
Protocol
Netmiko SSH
Output format
CLI text → regex parse
Credentials
NOKIA_USER / NOKIA_PASS
Connection
Pool · 60 s TTL · circuit breaker
Why thread executor? SSH/NETCONF are blocking — they wait for the router to respond. FastAPI is async (event-driven). If blocking code ran directly in the async loop, the entire web server would freeze while waiting for the SSH response. run_in_executor() hands the blocking call to a separate OS thread so the event loop continues serving other requests.
🔌 MCP Client — vendor-maintained tools
MCP = Model Context Protocol. A standard way for LLMs to discover and call external tools without hardcoding them.
Why MCP for Jira but not devices?
🟣
Jira → MCP (mcp-atlassian)
Atlassian's community built and maintains 48 Jira tools. We just connect. If they add a new Jira API, we get it for free. Zero maintenance burden.
📡
Devices → Direct adapters
No official production-grade MCP server exists for Cisco IOS XR or Nokia SR OS. We control those adapters anyway — they're simple Python with no maintenance burden.
How MCPClient.start() works at startup
1.Read mcp_servers.yaml — find all enabled: true servers
2.Open persistent SSE connection to each server URL
3.Send MCP initialize handshake
4.Call list_tools() — server returns all 48 tool definitions
5.Store prefixed: jira_create_issue, jira_search_issues…
6.If connection drops → auto-reconnect once and retry the call

How role gates tools
dispatcher.get_all_tools(role) builds the tool list passed to the LLM. A noc user's list never contains Jira creation tools. The LLM cannot call what it cannot see — it would have to hallucinate a tool name that isn't in its schema list, which would be rejected by the dispatcher as "unknown tool."

🛡️ Read-only safety — 3 independent layers
All three layers must be independently bypassed for any configuration change to be possible. In practice: impossible without modifying source code.
1
System prompt instruction
The LLM is instructed in llm/prompts.py that it performs read and diagnostic operations only. It will decline requests like "shut down this interface" and offer to create a change ticket instead. This is baked into its instructions before every conversation.
2
_is_config_request() regex check — runs before the LLM is even called
In _run_chat(), the user's message is tested against a regex before any LLM call. If the message contains configure, apply, commit, rollback, shutdown, no shutdown, set, delete, modify, etc., the function returns a refusal immediately — the LLM and all adapters are never invoked.
re.compile(r"\b(configure|apply|commit|rollback|shutdown|set\s+|delete\s+|modify\s+)\b")
3
Tool schema design — write tools simply do not exist
None of the functions in cisco.py, junos.py, or nokia.py accept write commands. There is no push_config(), commit_changes(), or apply_config() function. Even if the LLM tried to invent a tool name, the dispatcher would return {"error": "Unknown tool"}.
