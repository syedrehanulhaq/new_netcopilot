End-to-End Request Flow

What happens from the moment you type a question to the moment you get an answer.

Step 1
You type a question
Interface: Browser / Slack / Teams
The web UI, Slack slash command, or Teams message sends a POST /chat request to the NetCopilot server with your message and session cookie. Slack requests additionally carry an HMAC signature that is verified before anything else runs.
POST /chat POST /slack/command POST /teams/webhook
Step 2
Rate Limiter
File: app.py — _enforce_rate_limit()
Before touching anything else, NetCopilot counts how many requests your IP has sent in the last 60 seconds. If you exceed 60 requests/minute, it returns HTTP 429 immediately. The counter is capped at 10,000 tracked clients to prevent memory exhaustion.
Pass → continue Fail → HTTP 429
Step 3
Authentication & Role
File: app.py — _get_role_from_request()
Your session cookie is verified — it's cryptographically signed with SESSION_SECRET. If invalid or expired, HTTP 403 is returned. Your role is extracted from the session: noc, noc-ticket, or admin. This role travels with the request for the rest of its life.
noc noc-ticket admin invalid → HTTP 403
Step 4
Build Context for the LLM
File: app.py — _run_chat()
Three things are assembled into a messages array before the LLM is called:

① Conversation history — last 12 exchanges loaded from memory.db so the LLM remembers what was discussed before.

② System prompt — built by llm/prompts.py. Tells the LLM who it is, what it can/cannot do, which vendor each device is, and what playbooks exist.

③ Tool list — assembled by dispatcher.py, filtered by role. A noc user gets 55 diagnostic tools. noc-ticket also gets 4 Jira tools. The LLM cannot call a tool it was never given.
memory.db → history prompts.py → instructions dispatcher.py → tool list
Step 5 — The Agentic Loop · app.py _agentic_loop() · max 10 turns
🧠
LLM called
GPT-4o / Claude receives your question + history + tools. Decides what to do next.
→
🔧
Tool call decided
LLM picks a tool and arguments, e.g. junos_get_bgp_neighbor_status(device="pe1")
→
⚡
Tool executed
Dispatcher routes to right adapter → SSH/NETCONF to device → real output returned
→
📋
Result appended
Device output added to the messages array. LLM is called again with the new context.
→
✅
Answer ready
No more tool calls needed. LLM writes the final plain-English answer.
Multiple tool calls in one turn run in parallel (up to 5 simultaneous device connections) · Hard cap of 10 turns per request
Step 6
Tool Dispatcher routes the call
File: adapters/devices/dispatcher.py
The dispatcher reads the tool name prefix to decide where to send it:

cisco_* → adapters/devices/cisco.py (Netmiko SSH)
junos_* → adapters/devices/junos.py (PyEZ NETCONF)
nokia_* → adapters/devices/nokia.py (Netmiko SSH)
jira_* → adapters/integrations/jira.py (REST API)
run_playbook → playbooks/runner.py

It also checks devices.yaml via registry.py to confirm the device's vendor before connecting.
cisco_* → cisco.py junos_* → junos.py nokia_* → nokia.py jira_* → jira.py
Step 7
Circuit Breaker + Credentials
Files: adapters/devices/pool.py · credentials.py
Before opening any SSH connection, two checks happen:

Circuit Breaker (pool.py) — Is this device currently isolated? If it has failed 3 times in a row, it's in OPEN state and all calls are blocked for 60 seconds. Returns an error immediately — no SSH attempted.

Credentials (credentials.py) — Fetches the device username/password. Checks settings.db first (UI-saved credentials), falls back to .env. Passwords are never logged — _scrub_error() strips them from all errors.
CLOSED → connect OPEN → blocked for 60s HALF-OPEN → one probe
Step 8
Device Connection (SSH / NETCONF)
Files: adapters/devices/cisco.py · junos.py · nokia.py
The adapter opens a connection and runs the appropriate command:

Cisco IOS XR → Netmiko SSH → show interface Gi0/0/0/0
Juniper Junos → PyEZ NETCONF → structured XML query
Nokia SR OS → Netmiko SSH → show port 1/1/1 detail

All commands are read-only show commands — there are no write tools. A 60-second hard timeout is applied via asyncio.wait_for — a hung device cannot block the server.
Read-only — no config push 60s timeout enforced
Step 9
Save to Memory & Return Answer
File: app.py — _save_memory() → memory.db
The LLM's final answer is ready. Before returning it:

Tool outputs are saved to memory.db — truncated to 800 chars each, prefixed with investigation findings. This means the next time you say "raise a ticket for that", the LLM still has the device data from this conversation.

The reply is streamed back to your browser/Slack/Teams in real time via SSE (Server-Sent Events) so you see words appearing as the LLM writes them.
saved to memory.db answer returned to you

Parallel Tool Execution

When the LLM decides multiple tools are needed in one turn, they all run simultaneously — not one after the other. Up to 5 device calls run in parallel.

Example — "Investigate the BGP outage on PE1"
junos_get_bgp_neighbor_status
Check BGP session state and last error
junos_get_interface_health
Check if the underlay interface is up
junos_get_isis_neighbors
Check IS-IS adjacency to same neighbour
syslog_search
Search logs for BGP events in the last hour
All four run at the same time. Total wait = slowest device, not the sum of all devices.

File Map — What Each File Does

app.py
The whole server. HTTP endpoints, auth, rate limiter, _run_chat(), _agentic_loop(), memory, metrics, Slack/Teams handlers.
llm/prompts.py
The system prompt. Tells the LLM who it is, what it can/cannot do, vendor rules, device inventory, ticket instructions.
adapters/devices/dispatcher.py
Air traffic control. Routes every tool call to the right vendor adapter based on the tool name prefix. Enforces role-based tool access.
adapters/devices/cisco.py
Cisco IOS XR adapter. 18 tools. SSH via Netmiko. Parses show command output into structured data for the LLM.
adapters/devices/junos.py
Juniper Junos adapter. 19 tools. NETCONF via PyEZ. Structured XML queries — more reliable than screen-scraping CLI.
adapters/devices/nokia.py
Nokia SR OS adapter. 18 tools. SSH via Netmiko. Parses Nokia-specific show commands.
adapters/devices/pool.py
Circuit breaker. Tracks device health per device. Isolates failing devices for 60s after 3 failures. Auto-recovers.
adapters/devices/registry.py
Device directory. Reads devices.yaml. Answers "what vendor is pe1?" so the LLM never needs to ask you.
adapters/integrations/jira.py
Jira integration. 4 tools: create, update, comment, close tickets. Calls Atlassian REST API via httpx.
credentials.py
Credential manager. Fetches passwords: settings.db first, .env as fallback. Strips credentials from all error messages.
devices.yaml
Device inventory. Maps device names to IPs, vendor, platform, site. The LLM reads this to know what exists and which vendor to use.
playbooks/playbooks.yaml
Diagnostic playbooks. Defines multi-step investigations by intent (link_down, bgp_down, etc.) — which tools to run, what evidence to collect.
playbooks/runner.py
Playbook engine. Runs the steps defined in playbooks.yaml, collects evidence, applies severity rules, returns a structured result to the LLM.
settings.py · settings.db
Settings store. SQLite database. Credentials and config changed via the UI are written here and take effect immediately — no restart needed.
memory.db
Conversation memory. Per-user history (last 12 turns) stored here. Tool outputs are saved so ticket creation later has the investigation context.
static/index.html
The web UI. Single-page chat interface. Connects to /chat/stream for real-time streaming of the LLM response as it's generated.
